### Выбранное решение: Kong Gateway

На основе проведенного сравнения для реализации API Gateway предлагается использовать **Kong Gateway**.

#### Обоснование выбора в соответствии с требованиями:

1.  **Маршрутизация запросов:**
    Kong предоставляет мощный и гибкий механизм маршрутизации. В отличие от стандартного NGINX, Kong позволяет изменять правила маршрутизации "на лету" через Admin API или декларативные конфигурации (decK) без перезагрузки сервиса. Это критически важно для CI/CD процессов в крупной компании, где микросервисы обновляются часто.

2.  **Проверка аутентификационной информации:**
    Kong обладает самой зрелой экосистемой плагинов для безопасности. 
    *   Поддержка **JWT Validation** позволяет проверять подписи токенов на стороне шлюза, не нагружая микросервисы.
    *   Интеграция с внешними Identity Providers (Keycloak, Okta) через плагины **OpenID Connect**.
    *   Возможность реализации **RBAC** (Role-Based Access Control) на уровне входа.

3.  **Обеспечение терминации HTTPS:**
    Kong эффективно выполняет роль SSL-прокси. Он поддерживает динамическую загрузку сертификатов для различных доменов (SNI). В связке с Kubernetes (через Kong Ingress Controller) и Cert-Manager процесс управления сертификатами полностью автоматизируется.

#### Дополнительные преимущества для компании:
*   **Observability:** Встроенная интеграция с Prometheus и Grafana для мониторинга и Jaeger/Zipkin для распределенной трассировки.
*   **Rate Limiting:** Нативная защита внутренних сервисов от перегрузок и DDoS-атак.
*   **Декларативный подход:** Поддержка методологии GitOps (хранение всей конфигурации шлюза в репозитории).
*   **Масштабируемость:** Возможность работы в режиме **DB-less**, что упрощает эксплуатацию и повышает отказоустойчивость системы.

### Заключение
Внедрение **Kong Gateway** обеспечит надежный фундамент для эксплуатации микросервисов, позволит централизовать сквозной функционал (безопасность, лимиты, логирование) и сократит время вывода новых сервисов в продакшн (Time-to-Market).

| Характеристика | RabbitMQ (Quorum Queues) | Apache Kafka | NATS JetStream |
| :--- | :--- | :--- | :--- |

### Выбранное решение: Apache Kafka

Несмотря на то, что RabbitMQ проще в начальной настройке, для **крупной компании** с микросервисной архитектурой я рекомендую использовать **Apache Kafka**.

#### Обоснование выбора в соответствии с требованиями:

1.  **Поддержка кластеризации и надёжность:**
    Kafka изначально проектировалась как распределенная система. Данные реплицируются между брокерами. Использование фактора репликации (Replication Factor) гарантирует, что при выходе из строя одного или нескольких узлов данные не будут потеряны, а система продолжит работу.

2.  **Хранение сообщений на диске:**
    В отличие от классических брокеров, Kafka — это распределенный лог фиксации. Сообщения не удаляются сразу после прочтения, а хранятся в течение заданного времени (Retention policy). Это позволяет микросервисам "перечитывать" данные в случае сбоев или при необходимости восстановить состояние (Event Sourcing).

3.  **Высокая скорость работы:**
    Kafka использует принцип последовательной записи на диск и Zero-copy передачу данных, что обеспечивает колоссальную пропускную способность. Это критично для крупной компании при обработке больших потоков событий (логов, транзакций, аналитики).

4.  **Поддержка различных форматов:**
    Kafka абсолютно нейтральна к формату данных (передает массив байтов). Однако в экосистеме Kafka есть Schema Registry, который позволяет строго контролировать структуру сообщений (например, через Avro или Protobuf), что важно для стабильности контрактов между микросервисами.

5.  **Разделение прав доступа:**
    Kafka поддерживает аутентификацию (SASL/SSL, Kerberos) и авторизацию через ACL. Мы можем четко разграничить, какие сервисы могут писать в топик `orders`, а какие — только читать из него.

6.  **Эксплуатация в масштабе:**
    Хотя Kafka считается сложной в настройке, в контексте крупной компании этот вопрос решается использованием:
    *   **Kubernetes Operators** (например, **Strimzi**), которые автоматизируют развертывание, обновление и масштабирование кластера.
    *   Устоявшихся практик мониторинга (JMX exporter, Kafka Exporter).
    Для микросервисов Kafka становится "становым хребтом", который выдерживает нагрузки, непосильные для традиционных брокеров очередей.

### Заключение
Выбор **Apache Kafka** обусловлен её способностью выступать не просто как средство передачи сообщений, но и как надежное хранилище событий. Это обеспечивает высокую отказоустойчивость и масштабируемость, необходимые для крупной информационной системы.
